# Agent corrections

One line per correction: what the agent had done → what I asked to change → why.

- Wrote chat replies in English → asked to write them in Portuguese → I review faster and more precisely in my own language; the repository (code, docs, commits) stays in English, as CLAUDE.md says.
- Planned to store the friendly failure text in `error_message` → keep Pixelforge's original message (or a technical description for our own codes) in the database and map the code to friendly text through a backend enum applied by `GenerationResource` → no UI copy in the database; the raw message is useful for debugging.
- Proposed a polling chain with no uniqueness guard → make `PollGenerationJob` `ShouldBeUniqueUntilProcessing` by generation id and dispatch poll attempt 1 only when `SubmitGeneration` sets `submitted_at` itself → never more than one polling chain per generation, while a running job can still dispatch its next attempt.
- Proposed the M3 flow without a rule about external calls and locks → never call Pixelforge inside a transaction or while holding a row lock; call first, then lock, re-read and apply → an HTTP call can take up to the 30 s timeout; holding a transaction or row lock that long blocks the webhook handler for the same generation (which must answer within 10 s or Pixelforge resends) and ties up a database connection. A rollback also can't undo an external call: if Pixelforge accepts the generation and our transaction then rolls back, we lose the record of something Pixelforge created and will bill.
- Proposed failure messages that name Pixelforge → provider-neutral copy, and update the existing messages that name it → users don't need to know the provider.
- Proposed answering 400 when the webhook secret is missing → answer 500 with an error log → a missing secret is our misconfiguration, not a bad request.
- Proposed narrowing `inProgress()` to "not final and created in the last 2 hours" so the page stops polling → keep `inProgress()` as "not final" and add a separate `recentlyActive()` for the page, with the window in `config/generations.php` → page polling is an interface rule and must not change the meaning of a domain method that other parts use.
- Built the generations page inside the starter kit's sidebar layout (side menu, composer and history: three columns) → use the header layout (top bar with logo and user menu, no side menu) for the generations page and Settings, with two full-height columns below → the reference pattern uses two columns, and a single-page app has nothing to put in a side menu.
- Reported M4's "nav and branding" as done while the starter kit's Welcome page, favicon and Laravel logo were still there → replace Welcome with our own landing and brand every screen (logo, name, tab title, favicon) → the evaluators will open the app; leftovers of the Laravel brand make the product look like an unfinished template, and a coherent identity on every screen is part of the product sense being evaluated.
- Reported the history card as done with an image frame that ignored the aspect ratio and cropped the image (`object-cover`), hiding the caption Pixelforge writes on it → frame with the generation's aspect ratio and the whole image (`object-contain`) → a 1:1 generation showed in a wider frame and the caption with the prompt wasn't visible.
- Showed "$0.0000" under "Charged" for failed generations → show "Not charged" → a row of zeros looks like an amount to double-check, or even a bug; words state the rule directly (failures are free), and the exact value stays in the tooltip.
- Showed failures in an image-sized block → a compact strip with the icon and the message → the image-sized block wasted space and gave failures more weight than the generated images; the strip keeps the history dense and the failure visible in the right measure.
- Gave the composer footer a top border and let the page grow with its content, so in a short window the footer was pushed off-screen → no border, a background one tone above the panel's, and a fixed page height on md and up so the panel scrolls on its own → the footer must stay separated from the content scrolling behind it, and fields must not look cut by it and, on an almost empty panel, the line was visual noise: the background tone separates the footer without drawing a border and still works when content scrolls behind it.
- Planned M5 as if the Laravel Cloud production environment had to be created and configured → check the existing environment, don't create it → it was created in Stage 0 and already tested with the skeleton (registration and login working).
- Recommended adding `laravel/cloud-cli` to `composer.json` → the user installs the CLI globally and authenticates; the agent proposes each command and the user approves it → the CLI is a personal operations tool, not an application dependency: in `composer.json` (even as dev) it would go into the lock file, every clone's install and CI, couple the code to one host, and serve no one but whoever operates the environment with their own account.
- Recommended reading `DEMO_USER_PASSWORD` through a new key in `config/app.php` → a separate `config/demo.php` with the email, the password and, in M6, the initial credit → `config/app.php` is the framework's and stays intact, and everything about the demo user lives in one place.
- Planned to operate production through the `cloud` CLI (`command:run` for the seeder, `tinker` for the cost check) → no CLI: the user operates the dashboard, deploys are approved pushes to `main`, the demo seeder runs in the deploy commands, and the user runs the cost query with a SQL client → the dashboard covers what is needed and avoids giving the agent direct access to production.
- Planned M5 with the user operating the dashboard and no CLI → back to the `cloud` CLI, installed globally and authenticated by the user: the agent runs the approved read-only checks and proposes each change one at a time for approval; the demo seeder stays in the deploy commands → operating through the dashboard was slow and error-prone on the user's side; with every command proposed and approved, the CLI is faster and more precise, and the CLI check is what found the missing managed queue.
- Justified 3 managed-queue workers by Pixelforge's limit of 3 generations in progress → the worker count doesn't control that limit; the 3 workers are only a cap on parallel jobs → a worker is busy only during the POST and the generation keeps running at Pixelforge without a worker, so the limit is still handled by the release with `Retry-After`.
- Kept the composer's values after submitting, as approved in M4 → clear the prompt once the server accepts the submission, keeping aspect ratio, quality and references (a first version reset the whole form) → with the prompt kept it looked as if nothing had been sent, and it was easy to submit the same prompt twice by accident; the generation shows up at the top of the history right away, so the prompt isn't lost.
- Left buttons with the default arrow cursor (Tailwind v4 no longer sets `cursor: pointer` on buttons) → enabled buttons show the pointer cursor → with Tailwind 4's default cursor, buttons didn't look clickable; the pointer is the expected sign that an element responds to a click.
- `SubmitGeneration` returned early on a retry once `submitted_at` was set, so a crash between recording the 202 and dispatching the poll left the generation with no fallback for lost webhooks → on a retry with `submitted_at` set and the generation not final, dispatch the poll again (the job is unique) → without it, a generation whose webhooks are lost never finishes, Pixelforge bills it and our records stop matching `/v1/usage`.
- `PollGenerationJob` didn't handle a 503 `overloaded` or unexpected errors, so they retried with no backoff until `retryUntil()`, spending Pixelforge's per-minute limit → treat `overloaded` like a 429 (release with `Retry-After`) and add `backoff()` → polling is the fallback for lost webhooks and must not burn the rate limit or die silently.
- Generations billed by Pixelforge that never reach a final state on our side weren't mentioned anywhere → document them as a known risk in the SPEC and the README, with the M7 report flagging the days that don't match → the task checks provider costs against `/v1/usage`, so the gap must be visible and explained.
- A submission blocked by our own throttle (429) showed Inertia's generic error page → show the message in the composer footer → the SPEC says a rejected submission keeps the values and shows the errors.
- Threw `UnexpectedValueException` directly in three places → named exceptions (`InvalidProviderGeneration`, `InvalidWebhookEvent`) → `CLAUDE.md` asks for named exceptions instead of generic ones.
- A generation waiting on Pixelforge's concurrency limit showed "Retrying…" → store why the last attempt had no 202 (`last_submit_error_code`) and show "Waiting for a free slot" for the concurrency limit → "Retrying…" reads like an error, while waiting for a slot is normal queueing.
- The card showed only the creation date → also show how long the generation took ("Completed in 18 s") → the SPEC lists timestamps on the card, and the duration is the useful one.
- `GenerationResource` read the time windows with `config()` → it receives them through its constructor, from the view model → the SPEC's Configuration section says classes receive config values through their constructors.
- Kept the skeleton's two `ExampleTest` files → delete them → they tested nothing of ours (one duplicated the landing test).
- The SPEC folder tree missed files added in M3–M4 (`Http/Concerns/FormatsMoney`, the webhook exceptions, the landing controller and view model) → update the tree → the SPEC is the source of truth for the structure.
